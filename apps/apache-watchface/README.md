# AH-64E Apache Watch Face

A Garmin Connect IQ watch face for the **fenix 7X Pro Sapphire Solar**, styled as a
monochromatic Tactical Green LCD/HUD readout: a big always-24-hour digital clock
centered in the display, with monospace/digital numerals and thin divider lines
separating each stat group — the look of an old cockpit MFD rendered on a modern
round MIP display.
(V2 briefly added an outer chapter-ring tick gauge; V2.1 removed it entirely per
client feedback — "the weird ring around the edge" — the second time a ring/gauge
has been added and rejected in this project, so it isn't coming back without being
asked again. V2.2 removed the dashed segment-style dividers under each stat row for
the same reason — client feedback: "remove the weird lines I don't like those, the
little dashed lines." **V6 removed the octagon-cut "MFD box" panel outlines
entirely** — every field used to sit inside a chamfered box border; the client
wanted those gone too, replaced by clean straight divider lines between
rows/fields — see "What's on screen" below for the current layout.)

**V6 layout**: every field still sits at a fixed pixel coordinate in
`source/ApacheWatchFaceView.mc` (not a proportional/dynamic layout), but the boxes
themselves are gone — see "What's on screen" below for the current matrix and
"Bezel margin check" for the corner-distance math every position was re-verified
against for its V6 position (several rows shifted a few px to make room for a
bigger clock and the new Timezone 2 field, so margins were re-checked, not assumed
to carry over from V2.1).

Field glyphs (battery, heart, boot/steps, solar rise-set, weather, Bluetooth,
notification bell) are pre-rendered, anti-aliased PNG bitmaps
(`resources/drawables/hud/`, regenerated by `tools/generate_hud_icons.py`) —
Monkey C's live vector fills have no anti-aliasing on a real MIP display and read as
crude/blobby at small icon sizes. The one exception, as of V6, is the top banner:
it used to be a baked bitmap with the literal text "AH-64E" drawn into it, but a
static bitmap can't reflect a user-editable string, so it's now live vector text
(`Fonts.headerFont()`) reading a configurable `airframe` property instead — see
"Configurable fields (V6)" below. Divider lines and the battery's proportional
charge fill stay vector-drawn (`source/HudDraw.mc`), since flat lines/rects don't
have the anti-aliasing problem bitmaps were introduced to solve.

**Status: builds and runs clean.** This has been compiled with the real Connect IQ
SDK (monkeyc) and run in the simulator (monkeydo) for both `fenix7xpro` and
`fenix7xpronowifi` with no crashes, including forced worst-case screenshots (Always-
On mode, `"88:88"` clock, 10-char airframe / 8-char squad strings). Local
environment is already set up on this machine — see below.

### Color scheme (V6 — single hue, brightened)

Everything is **Tactical Green** (`0x39FF14`, unchanged) in day mode and a dimmer
green in Always-On — there are no per-field accent hues (V1's amber solar icon /
red heart icon are gone; both are plain green now). **The only exception is the
battery field**, which dynamically swaps to **Tactical Alert Red** (`0xFF1E1E`)
below 15% charge — fill, label, and value text all switch; the pre-baked chrome
outline+nub bitmap itself stays green (no runtime bitmap tint API), so the field
still reads clearly as an alert even though one bitmap layer doesn't recolor.

**V6: brightened, especially Always-On.** `AOD_GREEN` raised `0x1B7A0A`→`0x26AA0D` —
the old value was ~2.1x dimmer than `TACTICAL_GREEN` channel-for-channel, which
(sRGB gamma is non-linear) reads as roughly a 5x *perceptual* brightness drop, not a
2x one. Raised to a flat 2/3 scale of `TACTICAL_GREEN`'s R/G/B — still legibly
dimmer than day mode (Always-On needs to stay visually distinct at a glance) but far
less crushed. The divider-line colors (`PANEL_DAY`/`PANEL_AOD`, previously the box
outline colors) were raised the same way (`0x1C5E10`→`0x1F8C0B`,
`0x0E3A08`→`0x155E07`) — still kept dimmer than `textColor()` in both modes so
dividers read as framing, not information.

### Fonts (V2.1 — sizes scaled down ~1/3 for legibility, custom typeface attempted, real fallback shipped)

**V6 update**: `FntTime` **37→44px** and `FntSeconds` **19→23px** (see
`source/Fonts.mc:timeFont()/secondsFont()`) — boxes were removed in V6 (see "What's
on screen" above), freeing box-border padding that was reallocated to a bigger
clock, the client's explicit V6 ask. Verified against a forced `"88:88"` +
2-digit-seconds worst case, same doctrine as every font-size change below.

The spec asked for a custom "MFD-64" family at `FntTime` 52px, `FntSeconds` 34px,
`FntDate` 24px, `FntMetrics` 20px, `FntHeader` 18px, `FntFooter` 16px, `FntLabels`
10px, substituting Consolas Bold / Impact TTFs since "MFD-64" doesn't exist. A real
screenshot of the V2 build showed text overlapping/unclear at those sizes, so V2.1
scaled every named size down ~1/3 (relative hierarchy between roles unchanged, just
smaller overall): `FntTime` **35px**, `FntSeconds` **23px**, `FntDate` **16px**,
`FntMetrics` **13px**, `FntHeader` **12px**, `FntFooter` **11px**, `FntLabels`
**7px** — see `source/Fonts.mc`.

**V2.2 client polish pass** changed two of these: `FntTime` **35→33px** (client:
trim the clock font a couple px) and `FntDate` **16→8px**, an explicit halving, not
a small nudge (client: "half the size it currently is"). `FntDate`'s null-load
fallback constant was also switched from `FONT_MEDIUM` to `FONT_XTINY` to match —
falling back to a medium-sized enum font at an 8px call site would look wildly
inconsistent if `getVectorFont()` ever failed to resolve.

**This custom-typeface substitution was actually attempted this session**, not assumed to work: `consolab.ttf` was copied
into `resources/fonts/`, declared via a `<font>` resource, and run through the real
`monkeyc` compiler. Real error:

```
Unable to process 'font' resources: "9B" is not a valid key/value pair.
```

The compiler parses a `<font filename="...">` as AngelCode BMFont **text** format (see
the SDK's own `doc/docs/Core_Topics/Resources.html` "Fonts" section) — it tried to
read the raw TTF's binary header as BMFont key/value text and choked on the first
non-ASCII byte sequence. Separately, `fontType`'s schema (`bin/resources.xsd`) has no
"size" attribute at all — a compiled font resource is a bitmap glyph atlas baked at
**one** fixed pixel size, so getting 7 sizes out of 2 files would mean generating 7
separate BMFont atlases, not a plain resource declaration.

**Fallback shipped**: `source/Fonts.mc` uses `Graphics.getVectorFont()`, a real
on-device vector font engine (fenix7xpro is a supported device for it) that takes an
arbitrary pixel `:size` — so all 7 spec'd pixel sizes are honored exactly, just backed
by one of the device's built-in vector faces (`sourceSansPro` for the
Consolas/numeric role, `leagueGothic` for the Impact/header role) instead of the
literal Consolas/Impact files. Every call site falls back one step further to a fixed
`Graphics.FONT_*` enum constant if `getVectorFont()` ever returns null. Confirmed
rendering correctly in the simulator (not silently falling back) — the date/label
text visibly uses the bolder `leagueGothic` face, distinct from the clock/metrics
numerals.

**Licensing note for later**: this fallback sidesteps the question entirely (system
vector fonts, nothing embedded), so there's nothing to flag for the current build.
If a future pass ever does embed a licensed font file directly (e.g. building the
BMFont-atlas pipeline to actually use Consolas/Impact), remember Microsoft's EULA is
more restrictive about redistributing the raw font file in shipped software than
about local/personal use — swap for an OFL-licensed face before any public Connect IQ
Store submission.

### Bezel margin check (V2.1 full-matrix rework)

The V2 client-spec matrix was implemented literally, compiled, run, and
screenshotted (native `PrintWindow`, not eyeballed) — this is what actually turned
up the "overlapping/unclear" defect. Real corner-distance math (worst corner =
`sqrt(max(|left-cx|,|right-cx|)^2 + max(|top-cy|,|bottom-cy|)^2)` against the true
140px bezel radius) found:

- **Battery/HR boxes** (20,32,92,46 / 168,32,92,46): worst corner ~161px from
  center — **21px past** the visible 140px-radius circle, the single worst offender
  in the matrix.
- **Date box** (34,216,212,34): bottom corners ~153px from center — 13px past.
- **Steps/Solar/Weather/Title boxes**: all within ~0–1.4px of the edge —
  effectively zero real margin.

Every box was resized/repositioned to a verified positive corner margin (most land
at 8–13px) — narrowing width bought far more margin per pixel than moving a box
vertically, since rows this close to the top/bottom pole of the circle already
spend most of their radius budget on the vertical term. Two things this process
caught that the geometry formula alone wouldn't have:

- **An initial "push down" of the Weather box/Footer (Weather Y=252, Footer Y=272)
  looked margin-safe on paper but rendered visibly dim/soft in a real screenshot** —
  the round display's physical edge curvature softens content in roughly the last
  ~15px of radius regardless of what the corner-distance math says. Both were
  pulled back toward center instead (Weather net 2px *up* from V2's original
  Y=250, Footer 2px up from V2's Y=270) — legibility over the literal direction of
  the ask, confirmed by re-screenshotting until the text read as crisply as every
  other field.
- **The Solar box's "NEXT SOLAR" label overflowed past its own right border** once
  the box was narrowed for margin — caught in the same screenshot pass, fixed by
  shortening the label to "SOLAR" (matches the terseness of the other box labels:
  PWR/HR/STP) instead of widening the box back out and re-losing the margin fix.
- **Bluetooth/bell status icons** flanking the Weather box: at that row's vertical
  position there is ~78px of bezel-safe half-width available against the box's own
  40px half-width — ~38px of slack per side, better than V2's ~14px but still the
  tightest row on the face. These two icons stay deliberately tiny (12px) and
  tucked close to the box edges rather than given normal breathing room.
- **V2.2 polish pass**: growing the Weather box (bigger icon/temp text, moved up
  per client feedback) re-opened this exact margin question — re-verified with the
  new (96,243,88,20) box: worst corner ~130.6px from center, a 9.4px margin, still
  comfortably inside the >=6px convention used throughout. The Date box above it
  was also trimmed (28→22px tall) to free the vertical gap the Weather box needed
  to move up into, without touching its own bezel margin (it went from ~13px to
  ~20px margin, i.e. safer, not tighter).

### Bezel margin check, V6 addendum (box removal + bigger clock + new Tz2 row)

V6 removed every box border and reallocated the freed padding into a bigger clock
and flat 4px row-to-row gaps (a 1px divider line at each gap's midpoint) — this
shifted several rows by a few px, so every position was re-checked against its
**new** Y, not assumed to carry over from V2.1:

- **Clock** grew to (28,79,224,84) — H 72→84, the main lever behind the bigger
  font. Still centered on X=140; ~239px is the real bezel-safe width ceiling at
  this row's worst-case Y (top edge, dy=61), so the 224px width wasn't the
  bottleneck and was left alone. Worst corner ~127.5px from center, ~12.5px margin.
- **Steps/Solar** shifted down 5px to Y=171 to make room above for the clock —
  margin tightened from ~13.5px to ~11.8px, still comfortably ≥6px.
- **Date/Timezone2** is a brand-new combined two-field row (task 4) — the
  tightest new margin in the whole matrix, ~7.9px at dy=102 with both fields'
  outer edges at dx=84 against an ~86.9px ceiling. Verified, not assumed, since
  there was no V2.1 precedent for a two-field row this low on the face.
- **Title and Footer flourish lines** (the flanking ticks around the airframe
  name / squad callsign) are now driven by a *user-editable string*, not a fixed
  label — a long name could in principle push the flourish past the bezel at
  these near-pole rows. Capped with `TITLE_MAX_HALF_W`/`FOOTER_MAX_HALF_W`
  constants (52px / 42px) computed the same corner-distance way, and the
  flourish is skipped entirely (text-only) if it would need to exceed the cap.
  Verified against a forced 10-char airframe / 8-char squad worst case — the text
  itself stayed clear of the bezel, and the flourish correctly disappeared for
  the airframe case (10 chars was wide enough to trip the cap) while still
  showing for the 8-char squad case.

## 1. Set up your local environment (on another machine)

Already done on this machine (see above). On a different machine — e.g. if your
brother wants to build it himself rather than just receiving a `.prg` — here's what's
needed:

1. **Install the SDK Manager GUI**, from the
   [Connect IQ SDK page](https://developer.garmin.com/connect-iq/sdk/), *or* the
   [connect-iq-sdk-manager CLI](https://github.com/lindell/connect-iq-sdk-manager-cli)
   (what was used here — scriptable, but it's a third-party tool, not Garmin's own).
   Either way it's gated behind a free Garmin account login + accepting Garmin's SDK
   license.
2. **Install a JDK** (Java 17+) — the compiler (`monkeyc`) is a JVM tool and won't run
   without one. [Microsoft's OpenJDK 17](https://learn.microsoft.com/en-us/java/openjdk/download)
   is a safe, official pick.
3. **Install the SDK + device files, including fonts.** If using the CLI:
   `connect-iq-sdk-manager device download --manifest=manifest.xml --include-fonts`
   — the `--include-fonts` flag is easy to miss and its absence causes a
   confusing runtime crash (`Invalid Font Specified`) that has nothing to do with
   which font you picked in code; see "Bugs found" below.
4. **Install VS Code + the Monkey C extension** (`garmin.monkey-c`) — Garmin's
   current official toolchain (the old Eclipse IDE is deprecated).
5. **Generate a developer key** (one-time): `openssl genrsa -out developer_key.pem 4096`
   then `openssl pkcs8 -topk8 -inform PEM -outform DER -in developer_key.pem -out developer_key.der -nocrypt`.
   Keep it outside any repo — **never commit it**.
6. **Device id**: both `fenix7xpro` and `fenix7xpronowifi` in `manifest.xml` are
   confirmed valid — both downloaded and compiled successfully, so no manifest edit
   is needed regardless of which exact fenix 7X Pro variant you have.

## 2. Build & run in the simulator

- Command palette → `Monkey C: Run` → pick **fenix7xpro** (or whichever id you
  kept) → this builds and launches the Connect IQ Simulator.
- In the simulator, use the **Sensors** menu to fake heart rate/step data, and
  the **location** picker so `Weather`/sunrise-sunset have something to compute
  from (both are `null`-safe in the code — they'll just show `--` until a
  location/weather source is available).
- Toggle Always-On mode via **Settings → Display Mode → Always-Active** (vs.
  `High Power`) in the simulator's menu bar — this is what actually fires
  `onEnterSleep()`/`onExitSleep()` in the view, not the separate `Settings → Sleep
  Mode` checkbox (that one had no observable effect on the watch face in testing).
  Confirmed clean transitions both directions (banner/seconds appear-disappear,
  colors shift phosphor-green ↔ dim monochrome green) with no crash in either
  direction, verified via `monkeydo` + simulator screenshots, not just assumed from
  the `_isSleeping` branches compiling.

## 3. Sideload to your watch (or send the `.prg` to someone else)

1. Command palette → `Monkey C: Build for Device` → produces a `.prg` in `bin/`.
2. Connect the watch by USB — it mounts as a mass-storage drive.
3. Copy the `.prg` into `GARMIN/APPS/` on the watch.
4. Eject/disconnect. The watch face appears in your watch face list within a
   few seconds.

(Garmin Express can also push it, but the drag-and-drop above is simpler for
iterating during development.)

**A compiled `.prg` is just a file — you can email it, and no device needs to be
plugged into this machine for that.** Building only needs the SDK; installing only
needs *the target watch* plugged into *whichever* computer is doing the install. So:
compile once here, send the `.prg` to your brother, and he plugs his own watch into
his own computer and drags it into `GARMIN/APPS/` — same 4 steps above, just on his
end. The one requirement: his watch has to be the same device id this was built for
(`fenix7xpro` / `fenix7xpronowifi`) — a `.prg` is device-specific, it won't install
on a different Garmin model. If he has a different watch, add his device id to
`manifest.xml` and rebuild.

## 4. Publish to the Connect IQ Store

1. Register as a Connect IQ developer (free) at the
   [Connect IQ Developer Portal](https://apps.garmin.com/developer/).
2. Command palette → `Monkey C: Export Project` (or `Build for App Store`) to

3. In the developer portal, create a new app listing, upload the `.iq`, and

One thing worth knowing before you submit: **"AH-64E Apache" is real Boeing
branding/trademark.** This watch face doesn't use any Boeing artwork, name, or
insignia in the code or icon — it's just a cockpit-instrument *aesthetic*
(phosphor-green digital numerals, thin divider-line framing). As of V6 the
"AH-64E" text itself is just the *default* value of the `airframe` setting, not
baked into the app — any soldier installing this can rename it via Garmin Connect
Mobile without recompiling. Keep the store listing's own name and description
generic ("phosphor HUD watch face" rather than "AH-64E Apache watch face") to stay
clear of any trademark issue, especially since this is a public store submission
and not just a personal sideload.

### Timezone 2 (V6)

A second, user-configurable time zone (`timezone2` setting, default Pacific) shown
beside the date. **There is no public Connect IQ API for the watch's native "Time
Zone 2" device setting** — `ClockTime.timeZoneOffset` only exposes the *primary*
zone already used by `System.getClockTime()` — confirmed against the local SDK
docs, so this couldn't just read a device setting. `source/TzCalc.mc` implements
the zone picker's live UTC offset (Pacific/Mountain/Central/Eastern/Alaska -8/-7/
-6/-5/-9h standard, Hawaii -10h and UTC +0h with no DST) plus manual US DST math
(2nd Sunday of March 2am through 1st Sunday of November 2am).

**A real bug was found and fixed during verification, not assumed away**:
`Gregorian.info()` always converts a `Moment` through the *device's own*
configured local timezone when producing calendar fields — even for a `Moment`
built from `Gregorian.moment()` with literal "UTC" field values. A first
implementation tried the same "build a shifted moment, read its fields back" trick
the rest of the app already uses for its own local time — for an arbitrary
non-device zone this silently re-applies the device's own offset a second time.
Caught in the simulator: with the host on CDT (UTC-5) and Pacific correctly at
UTC-7 (DST active), the displayed Tz2 time read ~5 hours short of correct — exactly
the host's own CDT offset leaking back in. Fixed by doing all epoch/day-of-week/
DST-boundary math with plain integer arithmetic on `Moment.value()` (raw UTC
epoch seconds), never through `Gregorian.info()`'s read path — see the comments at
the top of `source/TzCalc.mc` for the full derivation.

### Configurable fields (V6)

Heading toward a public/store listing means fields that used to be hardcoded for
one client need to be editable by any soldier installing this, with no recompile:

- **`airframe`** (`alphaNumeric`, max 10 chars, default `"AH-64E"`) — the top
  banner. Used to be a baked bitmap (`ah64e_banner.png`, generated by the now-
  removed `ah64e_banner()`/`_feather_wing()`/`_feather()` functions in
  `tools/generate_hud_icons.py`) with the literal text drawn into the image and
  wing-feather artwork flanking it — a static image can't reflect a user-editable
  string, so it's now live vector text (`Fonts.headerFont()`) with a simple line
  flourish instead of bitmap wings, for visual consistency with the rest of the
  V6 divider-line language.
- **`squad`** (`alphaNumeric`, max 8 chars, default `"BRAVO-4"`) — the footer
  callsign. Was already text-rendered (no bitmap involved), so this was a smaller
  change — just wiring the property in place of the hardcoded string.

Both are edited from the Garmin Connect Mobile companion app (Settings → this
watch face → the setting name), the same place the existing `dateFormatDDMM` and
new `timezone2` pickers live. Both are defensively length-clamped in code (not
just relying on `settings.xml`'s `maxLength`) and their flanking-line flourishes
are capped/skipped against a bezel-safe max width — see "Bezel margin check, V6
addendum" above.

## Battery optimizations, and how they're implemented

- **Weather refresh**: every 15 min while awake, every 45 min in Always-On
  (`DataCache.AWAKE_WEATHER_INTERVAL_SEC` / `SLEEP_WEATHER_INTERVAL_SEC`).
- **Heart rate refresh**: every 5s awake, every 60s in Always-On.
- **Solar event**: computed once per calendar day, cached.
- **Redraw only what changes**: there's deliberately no `onPartialUpdate()`
  override. Seconds are hidden in Always-On mode, so there's nothing that needs
  a per-second redraw while sleeping — without a partial-update handler, the
  system's default low-power behavior is to call `onUpdate()` once a minute,
  which already matches the brief.
- Battery % and step count are cheap local stat reads (no I/O), so those are
  just re-read on every draw rather than cached.
- All HUD bitmaps are loaded exactly once, in `onLayout()` (`loadIcons()`, guarded
  by `_iconsLoaded`), and cached in instance variables — never reloaded from
  `WatchUi.loadResource()` inside `onUpdate()`.

## Bugs found and fixed during the real compile/run pass

This was first written without the SDK available, then actually compiled and run in
the simulator. Six real issues turned up, now all fixed:

- `private function` inside a `module` (`HudDraw.mc`) — Monkey C's `module` doesn't
  support access modifiers, only `class` does. Compile error.
- Missing `import Toybox.Lang;` in `ColorScheme.mc` — `Number`/`Boolean` type
  annotations don't resolve without it. Compile error.
- `getInitialView()` return type — the base class expects the tuple-array syntax
  `[Views] or [Views, InputDelegates]`, not `Array<Views or InputDelegates>`.
  Compile error.
- `fillPolygon()` point arrays need the tuple type `Array<[Numeric, Numeric]>`, not
  a generic `Array<Array<Numeric>>`. Compile error.
- `settings.xml` used a `list` setting config bound to a `boolean` property (for the
  DD/MM vs MM/DD picker) — Connect IQ only allows `list` on `number`/`string`
  properties. Switched `dateFormatDDMM` to a `number` property (1/0).
- **Runtime crash**, not a compile error: `Invalid Font Specified` on the very first
  `drawText()` call, regardless of which font constant was used. Root cause: device
  *fonts* are a separate downloadable component from the device profile and SDK —
  downloading device support without `--include-fonts` leaves the simulator with
  font metadata but no actual glyph data. Fixed by re-running device download with
  fonts included. If you ever see this exact error on a fresh device install, this
  is almost certainly why.

V1's field layout computed each row's usable half-width dynamically against real
round-display geometry (`safeHalfWidth()` — `sqrt(contentR² - dy²)`). V2 replaced
this with the client's literal fixed pixel matrix (see "What's on screen" above) —
`safeHalfWidth()` is gone; every box is a hardcoded `(X, Y, W, H)` constant. The
round-bezel geometry check didn't go away, it just moved from "compute the safe
region and size the row to fit" to "implement a fixed matrix, then verify the
numbers against the same bezel math and a real screenshot" — see "Bezel margin
check" above for what that caught in the V2.1 pass (three boxes' corners were
genuinely past the visible circle, not just tight). Same rule as before: a `BUILD
SUCCESSFUL` says nothing about whether a box actually clips or two fields overlap —
always re-verify with `monkeydo` + a real screenshot (native Win32 `PrintWindow`, not
a browser tool) after touching any coordinate.

The `Weather.CONDITION_*` subset used in `HudDraw.mapConditionToBucket()` is
deliberately conservative (constants present since Weather's original 3.1.0
release) — there are ~50 more granular constants in the
[Weather API docs](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather.html)
if you want finer icon distinctions later.

## Customizing

- Colors: `source/ColorScheme.mc` (single Tactical Green hue + the battery-critical
  red threshold).
- Field positions/sizes: the `*_BOX_X/Y/W/H`/`DIV*` pixel constants near the top of
  `source/ApacheWatchFaceView.mc`, and the per-field `draw*Box` methods below them.
  Re-verify any change against the round-bezel math and a real screenshot — see
  "Bezel margin check" above. There is deliberately no outer ring/gauge and (as of
  V6) no box borders — don't re-add either without being asked again (see the intro
  note at the top of this file).
- Fonts: the 7 named roles in `source/Fonts.mc` (face name + pixel size per role).
- Icon shapes: `source/HudDraw.mc`.
- Refresh intervals: the constants at the top of `source/DataCache.mc`.
- Airframe name, squad callsign, timezone 2: user-facing settings, edited via
  Garmin Connect Mobile — no code change or recompile needed. Defaults live in
  `resources/settings/properties.xml`; see "Configurable fields (V6)" and
  "Timezone 2 (V6)" above for the implementation.
